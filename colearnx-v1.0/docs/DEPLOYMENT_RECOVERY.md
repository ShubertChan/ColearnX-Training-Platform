# CoLearnX 发布核验与恢复演练

发布负责人先在 GitHub 的 **Deploy staging** 运行记录中确认源提交、前端和 API 各自的实际版本、数据库迁移末项及发布结果。保留对应的发布归档。媒体网关和本机转码有独立版本，单独记录和复核。验收人员使用这份版本记录提交缺陷和复测结果。

## 核对已有发布

合并此配置后，可手动运行 **Verify an existing staging release**，输入先前成功的 Deploy staging 运行 ID。它从该运行的 GitHub 归档读取组件计划和构建清单，检查公开站点的静态文件哈希、API 健康、跨域和匿名访问限制，并记录两次就绪请求耗时。证据过期或线上版本已经变更时，核验失败；选用实际在运行的发布记录。没有定时保活，首次请求的耗时也不等于一次已确认的冷启动。

## 隔离恢复和回滚

手动运行 **Rehearse database recovery and application rollback**，输入上一个已知可用版本的完整提交 SHA。它必须是当前 main 的祖先，且两个版本使用相同的 Node 运行时。修改演练工具的 PR 也会以 PR 的基线和候选提交运行同一测试。工作流构建这两个提交的前端和 API，然后运行下面的演练。它只在回环地址创建新的 PostgreSQL 16 实例，使用合成账号和积分包。演练不接受外部数据库连接串。

1. 在源实例创建应用角色，通过项目迁移程序创建数据库结构并写入合成数据。将迁移文件和实际 ledger 的校验和逐项比对。
2. 用 PostgreSQL 的自定义归档格式备份应用库，随后改变源库的一条数据。在第二个空实例中预置集群角色，用单事务恢复归档并遇错停止。单库备份不会创建集群角色；角色的生产凭据应单独保管。
3. 核对恢复后的迁移时间、校验和、业务关联、权限、表、约束和索引。确认恢复结果反映备份时点，而源实例的后续修改仍然存在。
4. 在恢复库上启动候选前端和 API，用受限应用角色读取积分包。写入一条代表发布后活动的修改，停止候选版本，在同一端口启用旧前后端。再次检查页面与实际构建文件、就绪接口、受限接口和新数据。记录两个完整 SHA 以及耗时。
5. 保存脱敏 JSON，关闭演练创建的两个临时实例。该报告证明本次逻辑备份和兼容代码回滚成功；它没有测量 Neon 云端 PITR 的恢复时间或整个生产数据库的 RTO。

本地复跑需要 Git、Python 3、PostgreSQL 16 完整工具和仓库锁定的 Node 版本。在两个干净的检出中分别安装前端与 API 锁定依赖，并执行 API 和前端构建。前端使用本地相对地址作为 VITE_API_BASE_URL。Windows 示例（各变量指向自己的隔离工作目录）：

~~~powershell
python colearnx-v1.0/scripts/deployment/recovery-drill.py --candidate $CandidateCheckout --previous $PreviousCheckout --pg-bin $Pg16Bin --work-root $DrillWorkOnD --evidence $NewEvidenceFile
~~~

演练数据目录和证据应放在 D 盘；证据文件必须是新文件名。程序会尝试停止自己创建的实例；如果操作系统阻止停止，保留该临时目录供诊断。不要把测试路径换成项目的已有数据库目录。

## 真实事故时

1. 记录故障时间、受影响的组件、当前与上一个可用提交、最近已批准迁移、Render 部署 ID、Pages 构建和 Worker 镜像 ID。由部署负责人和数据库负责人共同确定恢复目标。
2. 对数据库恢复，先在隔离目标恢复到经批准的恢复点。校验 ledger、约束、必要的数据和运行角色权限，再核对 API、前端及关键读取；真实业务数据的访问和任何切换单独审批。
3. 对代码回滚，先验证旧代码能读取当前数据库，并确认旧代码不会破坏新增数据。使用已经测试的前后端组合；若不兼容，先做前向修复。数据库删除或回卷会丢失备份点之后的写入，不能作为应用回滚的默认步骤。
4. 恢复后检查健康、权限、跨域、组件版本、错误日志和积压任务。转码升级前确认旧批次已停止或排空，保存旧镜像；经验证后才更新部署基线。由测试人员复验受影响的业务，并将结果、责任人和恢复耗时补入共同测试记录。
