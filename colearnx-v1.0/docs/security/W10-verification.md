# 第十周 安全自测和密钥泄露演练

在从 `main@483c02e` 建立的测试环境中，四种攻击通过真实 API、业务权限和 PostgreSQL 16 重现。相同幂等键的并发下单暴露了一个可复现的 500，现已修复。这里只报告本地测试；没有使用真实订单、支付渠道、用户密钥或线上会话。

| 攻击 | 正向对照与攻击输入 | 观察到的结果 |
|---|---|---|
| IDOR（越权读订单） | 买家读取已购买订单；另一已登录成员分别请求该订单与随机订单号 | 买家 200；另一人两次均为同一 404 错误码，响应不含订单号。 |
| CSRF 绕过 | 对 refresh 和 logout 发送真实 Cookie，分别缺少令牌、混入另一会话的令牌、伪造来源或传 `Origin: null`；再以正确组合刷新 | 攻击均为 403，没有提前吊销合法会话；正确请求 200，新访问令牌能读取个人资料。另验证 staging 模式的 Cookie 带 Secure、HttpOnly、SameSite=None 和认证路径。 |
| 支付金额篡改 | 对应 1,000 个最小货币单位、500 积分的合成支付：先发伪签名，再发签名正确但金额为 1 的回调，最后发正确回调并重放 | 前两次返回 400，余额仍为 0；正确回调后余额为 500，重放后仍只有一笔入账。签名校验使用真实 Stripe SDK，本机生成请求，不连接 Stripe。 |
| 并发下单 | 客户端伪报单价 1、总额 1。六个同键请求购买定价 125 的内容；另四个不同键同时购买第二份内容 | 同键都返回同一笔 125 积分订单；异键只有一笔 201，其余 409。两份内容共扣 250，数据库恰有两笔订单、两条授权、两笔各 125 的借记。复用旧键改买其他商品返回 409。 |

**竞态修复。** 原结账逻辑先查幂等键、再插入。两个事务都查到“不存在”时，后一个插入触发唯一约束并向客户端返回 500。现在结账使用仓库已有的 `reserveIdempotency` 和 `completeIdempotency`，在同一业务事务中先占键，再记录结果。回归测试用数据库行锁确保请求真实重叠；不靠碰运气重复发请求。

## 密钥泄露演练

假设访问令牌签名密钥已泄露。每轮先让两个账号建立有效会话，再宣告事件、吊销测试库内全部未吊销的会话，用新密钥启动替代 API 进程。测试验证：

1. 原访问令牌在旧实例和新实例都失效；原刷新 Cookie 携正确 CSRF 令牌也不能换新会话。
2. 新实例允许重新登录。用泄露的旧密钥指向这个**新建的有效会话**伪造 JWT：旧实例仍会接受，新实例必须拒绝。这证明切换时必须摘除旧节点。
3. 新登录取得的 Cookie 可以正常刷新，刷新后的访问令牌可以读取用户资料。

2026-11-01 本地一次验收的三轮耗时为 **1,475 / 1,479 / 1,478 毫秒**，分别吊销 **22 / 3 / 3** 条未吊销会话（首轮包含之前测试建立的会话）。算术平均 **1,477 毫秒**。计时从宣告模拟泄露到完成旧凭据拒绝、新登录及刷新验证，包括启动新的 Node 进程；不含人工发现、托管服务发布或生产流量切换时间，不作为线上恢复承诺。

命令和讲解顺序见[演示脚本](W10-demo.md)。每次执行都重新计时并写 `release-report/security-w10/rotation.json`，只含环境、时间、轮数和计数；CI 以 `w10-rotation-<SHA>-<attempt>` 保存。该次完整数据库运行通过 46 组检查。F-13、F-19 的复评和实际部署步骤见[安全设计与风险复评](W10-security-design.md)。
